## 不应被复述丢掉的选择依据

- 固定程序限制运行时生成任意指令序列，不限制 C++ 计算；有限分支、数值运算和动态次数分别有不同表达策略。不要把“动态值”一律误认为需要动态程序。
- handler 可以完成只读 table 查询及 event 修改，不必为每次判断进入解释执行；确需持久副作用时再进入响应程序。费用预览与采用费用后才执行的效果分开，避免只看候选就消耗次数。
- stage 用于区分同一条指令恢复时需要解释的现场，不能为了罗列代码步骤无限增加 stage，也不能把一次不可中断的调用说成执行到一半暂停。
- 早期指令之间需要通过栈 ABI 配合，因此旧文要求调用方查阅完整布局。干净指令在彻底退出时恢复入口栈形状，响应程序通过事件 context 表达语义限制，使相邻指令不必再约定彼此的内部帧。外部输入仍需要特定暂停条件下的栈顶后缀，但不需要完整 ABI；后续可用 executor 输入接口进一步封装这部分访问。
- Context 检查放在编译入口，擦除后的运行时表示不重复存储 Context；wrapper 组合内部表示，避免通过可写基类破坏它的类型不变量。
- 定义源和游戏流程只能组合、配置核心给定的公开指令。这项约定始终有效；模板没有静态检查指令是否属于核心集合，并不使其他类型成为允许的扩展接口。
- 指令是领域操作；公共算法可以在 C++ helper 中复用。把它降低成许多小指令会增加槽位、分派次数和额外栈配合，并不是必需的复用层。
- 卡牌稳定槽位解决广播快照中的身份正确性问题；status 池主要解决大量小容器的分配与访问局部性问题。不要只比较结构字节数，也不要把第一版布局当成已经证明最优。
- 不复用槽位、只在明确安全点 cleanup 是不引入 generation 的前提；放宽此前提时必须重新评估旧理由，不能只保留“不用 generation”的结论。

以上理由的完整展开、示例和例外在对应专题及历史稿内。现有实现仍有需要单独确认的边界，见[文档范围与源码核对](reference_scope.md)。
