# 执行栈布局与搬迁约束

本页保存栈和帧为何这样组织、哪些访问形态能成立，以及实现重入指令时需要维护的条件。公开操作签名见[frame_stack](../reference/utils/frame_stack.md)。

来源：提交 `b3d6c50` 中的 `docs/zh/old/stack.md`。在原有帧布局、后缀定位和搬迁约束上，补充尾部子栈与可重新定位的 view。

executor stack 是执行期数据栈，用来保存 event、输入等待对象、广播游标和临时结算状态。旧文把它整体作为可按指令协议观察或写入的公开执行状态；当前 executor 不公开原始栈，观察与输入通过 execution_view 完成，帧布局由内部实现维护。独立栈工具的公开接口不授予对执行器现场的访问权限。stack 本身不保存独立的类型、帧目录、析构函数或复制函数元数据。

## Frame

一次 `push(...)` 创建一个 frame。普通 `top<T...>()` 和 `pop<T...>()` 访问栈顶的单个 frame，模板参数按 `push` 参数顺序书写。`frame_stack` 中的帧依次由动态数组前缀、固定字段、可选的一个尾部子栈组成；子栈使用 `substack_t` 描述，创建时传入 `substack()`。子栈内部只能保存不含 `substack_t` 的普通帧。

下文的 `A`、`B`、`C`、`Header` 和 `Input` 都是说明栈操作的示例类型，不代表执行器中的现行类型。

```cpp
const auto frame = stack.push(A{}, B{});
auto&& [a, b] = frame;

auto&& [same_a, same_b] = stack.top<A, B>();
stack.pop(frame);
```

`push` 返回新增 frame 的 view。`top` 也返回帧 view，具体类型可随访问形态变化；即使只访问单个对象也使用结构化绑定：

```cpp
const auto frame = stack.top<Input>();
auto&& [input] = frame;
```

帧 view 是非持有 view。普通 `frame_view` 保留原来的帧尾指针形式。对普通 view，后续可能扩容的 `push` 或 `reserve` 后重新取得；对应帧被 `pop`、`clear`，或 stack 被移动、赋值、交换后也不能继续沿用。

该规则不表示每次 `push` 必定重分配；当前实现容量充足时只推进栈顶。栈顶含子栈时另有可重新定位的 view，保证同一次取得的帧 view 可以在子栈增删后再次 `get`；但之前已经取得的引用、指针和 span 仍可能失效。这个区别不要求字段引用自动追踪搬迁。

## Object

stack object 必须平凡可复制、平凡析构，且对齐不超过 `std::max_align_t`。非平凡对象、局部引用、以及依赖外部生命周期的 `std::span` 不应直接作为 stack object 保存。

若需要变长数据，使用栈内动态数组，而不是把外部 span 存入 stack。

## Dynamic Array

动态数组通过 `dynamic_array<T>(...)` 压入，只能集中出现在 frame 开头。访问时在模板参数中写作 `T[]`；可变 stack 返回 `std::span<T>`，只读 stack 返回 `std::span<const T>`。

```cpp
const auto frame = stack.push(
    dynamic_array<std::uint32_t>(count),
    header
);
auto&& [values, header_ref] = frame;
```

传入无符号整数时只指定数组长度，不初始化元素；数组内容必须由调用方随后通过返回的 span 写入后才能读取。传入 range 时复制 range 内容，其元素值类型去掉 const 后必须与 `T` 相同。range 必须在计数与复制期间保持长度和内容一致；没有大小信息的 range 必须支持重复遍历，不能使用计数后即被消费的单遍来源。

## Top

`top<T...>()` 的模板参数必须和当前栈布局协议一致。调用方有责任保证类型、顺序和 frame 边界正确。

对最上层 frame，`top<T...>()` 可以访问该 frame 的固定部分后缀：

```cpp
stack.push(dynamic_array<std::uint32_t>(count), header, Input{});

auto&& [input] = stack.top<Input>();          // 固定部分后缀
auto&& [head, input2] = stack.top<Header, Input>();
```

输入实现可以把输入区放在 frame 尾部的完整固定对象序列中，由对应 execution_view 的参数式操作定位；外层不再读取指令或改写原始输入槽。stack 本身不记录哪些后缀对象是输入，也不检查输入类型。

动态数组不属于可单独后缀访问的固定部分。若 `top<T...>()` 中包含动态数组，则它必须描述整个 frame：

```cpp
auto&& [values, head, input] = stack.top<std::uint32_t[], Header, Input>(); // 整个 frame
```

不要写只覆盖一部分动态区域的 `top`，例如从第二个动态数组开始访问，或只访问动态数组而跳过后面的固定部分。只有当整个 frame 本身就是该动态数组时，`top<T[]>()` 才是完整 frame 访问。

有子栈时，后缀必须包含最后的 `substack_t`。例如 `top<Input, substack_t>()` 可以观察固定字段与子栈，而 `top<Input>()` 不会自动跳过末尾子栈。

## Pop

`pop<T...>()` 必须按完整 frame 弹出，模板参数应当和对应 `push(...)` 创建的 frame 匹配。不要用固定后缀 view 或固定后缀模板参数弹出 frame。

推荐在消费 frame 时保存完整 view，并直接传给 `pop`：

```cpp
const auto frame = stack.top<Input>();
auto&& [input] = frame;
const auto selected = input.selected;
stack.pop(frame);
```

`pop(view...)` 用于弹出一个或多个连续 frame。传入多个 view 时，按从下到上的顺序传入，通常直接使用多 frame `top` 的返回值：

```cpp
auto&& [lower, upper] = stack.top<frame<A, B>, frame<C>>();
stack.pop(lower, upper);
```

传给 `pop(view...)` 的 view 必须来自完整 frame 访问。不要把 `top` 取得的固定后缀 view 传给 `pop`。弹出含子栈的父帧会连同内部全部帧一并移除；对子栈调用 `pop` 只改变其内部帧，不会把子栈本身从父帧中移除。

## Multiple Frames

需要同时观察多个连续 frame 时，使用 `frame<...>` 分块。每个 `frame<...>` 都应描述完整 frame，返回值按从下到上的顺序排列。

```cpp
stack.push(A{}, B{});
stack.push(C{});

auto&& [lower, upper] = stack.top<frame<A, B>, frame<C>>();
auto&& [a, b] = lower;
auto&& [c] = upper;
```

多 frame `top` 用于组合协议边界处的读写。若后续在所属栈压入新 frame，应重新取得这些 view。若只是最后一帧的子栈增删，返回的所有 view 则按下面的规则重新定位。

## Substack

子栈不另外分配内存。其内容紧接普通部分，尾部保留长度记录；即使没有内部帧，这个记录也不能消失。

```text
低地址
动态数组元素 | 填充 | 数组描述符及固定字段
                                       ↑ P：普通部分的帧尾
子帧 A | 子帧 B | …… | 子栈长度记录
                                       ↑ E：整个父帧的帧尾
高地址
```

尾部直接存储一个 `size_t`，表示内部帧占用的字节数，记录空间按 `max_alignment` 对齐。由 `E` 减去记录空间和内部长度即可得到 `P`。普通字段和数组描述符仍从 `P` 向前定位，因此子栈增长不会搬动前面的固定字段，也不必修改数组描述符。

子栈追加时，以旧长度记录的位置为内部栈顶压入新帧，再在末尾重建长度记录。弹出时反向处理。整个操作只调整末尾内容，所有内部帧仍按原有异构帧规则排列；没有新增逐帧类型编号或析构表。

子栈内部不允许再次包含子栈，因此一次增删只需移动并更新一个尾部长度记录。同一个 `frame_stack` 可以有多个帧分别带有子栈，只有栈顶帧中的子栈可以增删内部帧。较早帧中的子栈只能访问已有内容，元素可修改性仍由 const 属性决定。

父帧不再位于栈顶时无需转换、封闭或记录额外状态。重新取得的 view 只提供符合当前位置的能力；旧的栈顶 view 不得在父帧被其他帧覆盖后继续沿用。恢复栈顶关系后可以重新通过 `top` 取得可增删访问。

## 子栈 view 的重新定位

访问形态在模板实例化时决定 view 的位置表示：

| 访问形态 | 位置表示 | 子栈增删权限 |
| --- | --- | --- |
| 单帧或后缀含子栈 | 仅持有所属 stack 指针，访问时重新计算栈顶 | 可写时允许 |
| 多帧访问的末帧含子栈：末帧 | 同上 | 可写时允许 |
| 上述多帧访问中的较早帧 | stack 指针和相对于整块存储起点的帧尾偏移 | 不允许 |
| 其他形态 | 原来的帧尾指针 | 不允许改变非栈顶子栈长度 |

子栈内部的 `top` 返回普通帧 view。父栈多帧访问所得较早帧的相对尾偏移不会随栈顶帧的子栈增长改变，也不会在整块存储扩容时失效。

普通访问不引入新的运行期模式分支或额外位置字段。重新定位只保证帧 view 能再次访问仍存在的数据，不保证已经返回的字段引用与 span 稳定，也不使 view 可以在父帧移除、stack 移动或交换之后继续使用。

## 从帧尾定位固定后缀

核对位置：[utils/stack.hpp](../../../include/givm/utils/stack.hpp)。固定元素的偏移从普通部分帧尾向前按类型尺寸和对齐计算，帧总大小再按 `max_alignment` 对齐。普通 `frame_view` 只保存帧尾指针与编译期类型信息；读取时由模板重新算出偏移。含子栈时先由尾部长度定位普通部分，再沿用这些偏移。因此相同尾部类型序列可以在不知道此前固定字段的情况下定位后缀。

动态数组在固定区保存 `dynamic_array_span{ offset_to_frame_end, count }`，元素本体位于整帧的动态前部。描述符使用相对帧尾的偏移，而非存储内绝对指针；整块栈搬迁后，数组位置可以由新帧尾重新计算。

```text
低地址                                                     高地址 / 帧尾
动态数组元素（逐数组对齐） | 填充 | 数组描述符 | 固定字段 | 输入等固定后缀
```

动态数组必须连续位于类型序列开头；含动态数组的 `top` 按使用约定需要描述整帧。若从第二个动态数组起读，但保留其后全部字段，当前偏移算法仍可能定位该数组的描述符和元素；问题在于该 view 的 `aligned_begin()` 将指向第二个数组的起点，不能再作为原帧起点用于弹栈或定位更低的帧。若连后面的固定字段也跳过，则连描述符相对帧尾的位置都无法按原布局计算。只有固定后缀属于独立观察的约定；弹出帧始终需要完整类型序列或完整 view。

多帧 `top` 访问 `N` 帧时，从最上方已知帧尾开始，按从上到下的顺序计算 `N - 1` 个帧边界，以较高帧的对齐起点作为较低帧的帧尾。各帧尾保存在局部定长数组中，随后按从下到上的顺序一次构造返回的 view 元组。单帧形式直接构造返回值，不建立这个数组。

按帧描述弹出多帧时，只用一个当前位置依次经过 `N` 个帧边界，取得最低帧的起点；不调用 `top` 或构造 view 元组。普通栈最后更新一次栈顶，子栈则在确定最终位置后移动并更新唯一的尾部长度记录。

`pop(view...)` 直接使用第一个完整 view 的起点作为移除边界。它不逐项验证传入 view 是否连续，也没有运行时类型检查来修复错误边界。

## 复制、扩容与对象选择

栈的复制构造复制已用字节，包括子栈的全部内部帧与长度记录；容量不够时按新大小的 `bit_ceil` 分配并搬迁已用字节。`reserve` 则直接按指定容量重新分配，即使请求的容量并不更大，旧的原始帧尾指针 view、字段引用和 span 也不能沿用。`clear` 和 `pop` 只改变栈顶，不逐对象调用析构。

因此“不在栈里保存依赖外部生命周期的 span 或局部引用”是保证快照可独立继续的设计约束，不仅是检查类型是否平凡可复制。一个指针或 span 在 C++ 类型层面可能满足平凡复制，逐字节复制它也不会复制其指向的数据。需要随执行器复制的变长内容应放入栈自己的动态数组。

动态数组的无符号长度形式只分配空间，range 形式先计数再复制；对无大小的 range，要特别检查第一次计数会不会消费数据。连续范围可按字节复制，非连续范围逐元素复制，但二者都不为单遍数据源提供自动缓存。

本页解释内存搬迁策略，不定义可持久化的二进制格式；字节序、类型大小、对齐、代码指针及外部引用仍依赖构建环境。
