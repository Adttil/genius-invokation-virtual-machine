# 伤害组与元素反应的责任边界

伤害中的反应加成、扣血后的击倒处理、元素反应本体分别承担不同责任。伤害组规定这些处理与完成通知的边界；公开输入见 [damage](../../reference/definition/events/damage.md)，命令契约见 [deal_damage](../../reference/definition/commands/deal_damage.md)。

## 初始输入与实际伤害

每条 `deal_damage` 拥有自己的结算组。固定 `damages` 在编译时复制；动态模式消费 `input_count` 个 `damage`。固定的是入口输入数量，不是最终伤害数量：范围目标按执行时存活角色展开，元素反应还会派生新的伤害。

一条初始描述开始处理时才解析相对目标或展开范围。范围记录具体角色 ID；已死的 ID 跳过，不重定向到下一个角色。反应派生伤害排在引发它的伤害之后、后续原始伤害之前；派生的元素伤害可以继续引发反应。

对局继续时，所有扣血、击倒处理和附着先完成，再按实际伤害顺序进行每次 `after_elemental_reaction` 与 `after_damage`。缓存的是完成记录，不能提前调用响应函数而仅缓存返回入口，否则响应读到的牌桌仍不符合这个边界。任一次扣血后的击倒处理都可能提前终局，剩余伤害和完成通知随即停止。

组内前一次伤害的计算、减伤、扣血和附着仍然影响后一次伤害。该设计不把整组伤害计算成同一份牌桌快照，也不将命中同一角色的多个伤害自动相加。相邻 `deal_damage` 以及响应程序中的 `deal_damage` 是独立命令，不自动并入当前组。

## 伤害加成与元素后果分别接管

`damage_calculation::already_handled_reaction` 表示伤害侧反应加成已经处理。它不跳过扣血后的元素附着，也不会自动设置 `elemental_reaction_will_occur::already_handled`。后者用于接管元素反应本身，两者不能混为一次接管。

反应种类、参与反应前的附着和最终输入元素在计算响应结束后判定一次并保存。由伤害触发的反应前通知发生在扣血与击倒处理之后，仅在对局继续时进行。因此此时接管反应不能追溯修改伤害侧已经应用的加成，也不能重新判定成另一种反应。增伤倍率为何在加算结束后统一应用，见[指令设计备忘](../instructions.md#结算边界)。

## 完整反应效果的责任

旧反应设计要求：接管者设置 `already_handled` 后，负责全部替代效果，包括必要的元素附着修改；没有接管时，领域指令负责默认附着变化和其他默认反应后果。仅返回一段响应程序不表示已经接管，不能留下“默认处理被跳过，替代效果也无人完成”的缺口。

`after_elemental_reaction` 位于组内全部扣血与附着之后；由伤害引发时，它在对应伤害后通知之前。无反应的附着不应仅因为修改了附着就发送反应通知。独立 `apply_element` 沿用同样的派生伤害结算边界。

超导、感电和扩散的默认派生伤害由当前组直接处理，不依赖定义源再返回一段伤害程序。反应实体创建等默认反应后果尚未完成，见[源码问题清单](../reference_scope.md)。这说明实现尚有缺口，不改变默认处理或接管者应当完成整次反应的责任。

旧文把 `reacted_aura` 称作“参与反应的旧 aura”，不能据此把它收窄成仅包含被反应消耗的那部分附着；当前语义是反应开始前的完整目标附着快照。

## 扣血后的击倒处理

击倒处理紧接每次扣血，先于该次元素反应及整组的完成响应。当前尚未接入濒死复活广播：生命降至零时先检查双方存活情况，若判定终局则立即停止，不再清理该角色的 attachment 与充能。只有对局继续时才删除角色全部 attachment、清空充能，再处理元素附着；已经删除的 attachment 不参与后续完成响应。终局也会停止当前反应、剩余伤害及所有尚未执行的完成响应。

濒死广播应插入生命降至零的分支，在 attachment 与充能仍保留时执行，使角色自身 attachment 也能提供复活。广播恢复后重新读取生命；若已复活则直接继续，否则立即判定终局。只有对局继续时才删除 attachment、清空充能；终局不承担这些后续清理。这个恢复点属于伤害命令本身，不需要给通用执行上下文增加伤害状态，也不能将清理推迟至伤害后响应。

观察模式的 `health_reduced` 仍紧接扣血；恢复后先进入上述击倒处理，再处理元素附着。终局检查由伤害命令承担，不能要求定义源另接一条通用检查指令，见[指令设计备忘](../instructions.md#结算边界)。何时请求出战选择的规则见[击倒与延迟出战选择](entity_events.md#击倒与延迟出战选择)。

独立命令与组内反应派生伤害遵守相同的扣血后终局边界。例如外组 A、B 已扣血，A 的伤害后响应再执行致死伤害 C；C 扣血后判定终局时，C 自身和外组 B 的伤害后响应都不会再执行。不需要跨层协调最外组收尾或保存额外的嵌套层数。

## 组内存储与续点

每个组拥有一个固定头部和尾部子栈。第一个伤害记录直接存在头部中，后续记录按实际需要压入子栈；记录之间用相对整栈起点的偏移连接，扩容和执行器复制都不需要修正指针。一条记录先属于待处理链，本次扣血与元素处理完成后复用同一个链接加入完成链，避免同时保存多份事件副本。

正在处理的记录始终保留在对应链首：计算、扣血及反应广播期间由待处理链首定位，反应后及伤害后广播期间由完成链首定位，全部处理结束才推进链首。因此不再额外维护当前节点偏移。处理反应派生时先将当前记录移入完成链，再把派生记录插入待处理链首；这两个内部步骤之间没有响应调用，不改变伤害或通知顺序。已失效的待处理目标则直接推进链首，不加入完成链。

初始输入数量和指令区位置只初始化一次、会反复读取，仍缓存在组头部。动态输入紧邻组帧下方，读取时从已经取得的组头部地址减去固定布局位移定位，避免另外保存、读取输入边界；位移包含组帧前端的对齐填充。首节点内置方式仍保留，避免常见单伤害再追加一个子帧。优化以执行耗时为先，不能仅因某项信息可推导便移除缓存。

初始描述按游标读取，范围目标展开为具体 ID。反应派生记录插入待处理链的前端，保持派生先于原本后续伤害的顺序。只有当前广播帧弹出、组帧重新位于栈顶时才扩充子栈；指令续点负责在计算、扣血、反应和完成广播之间切换。调用结束时弹出整个组和该命令消费的输入，通用执行上下文与调用协议均不需要伤害专用字段。

普通模式只编入命令入口及五个广播恢复入口，分别恢复伤害计算、伤害结算、反应前、反应后与伤害后广播。观察模式额外编入扣血观察恢复入口，普通模式不保留这个槽位。准备广播后直接尝试执行；只有进入响应程序时才交还调度，并使用对应 opcode 恢复。切换下一条伤害及遍历完成记录都由局部循环完成，不另设无条件相邻执行的 opcode。

固定参数和动态输入在编译时选择不同的执行函数实例，逐项读取时不再判断输入来自程序还是栈。局部阶段函数用 `std::optional<execution_state>` 区分两种结果：空值表示本阶段已经同步完成、调用方继续循环；有值表示已进入响应程序、观察暂停或终局，应交还调度。阶段之间可以直接调用，但每次伤害完成都会返回循环，不形成随伤害数量增长的 C++ 递归调用链。

## 治疗完成量

治疗完成通知 `healed` 应记录实际恢复的生命值，不能把治疗前提出的数额直接当作最终恢复量。当前治疗事件类型已声明，核心治疗流程尚待补全；这一区分仍是实现应遵守的要求。
