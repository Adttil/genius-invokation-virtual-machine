# 伤害与元素反应的责任边界

伤害中的反应加成、元素反应本体、伤害后的击倒处理分别承担不同责任。这里保留这些边界和尚未落实的规则；公开字段见[事件 reference](../../reference/executor/events.md)。

## 伤害加成与元素后果分别接管

`damage_calculation::already_handled_reaction` 表示伤害侧反应加成已经处理。它不跳过扣血后的元素附着，也不会自动设置 `elemental_reaction_will_occur::already_handled`。后者用于接管元素反应本身，两者不能混为一次接管。

由伤害触发的元素反应通知发生在扣血之后，因此此时接管反应不能追溯修改伤害侧已经应用的加成。增伤倍率为何在加算结束后统一应用，见[指令设计备忘](../instructions.md#结算边界)。

## 完整反应效果的责任

旧反应设计要求：接管者设置 `already_handled` 后，负责全部替代效果，包括必要的元素附着修改；没有接管时，领域指令负责默认附着变化和其他默认反应后果。仅返回一段响应程序不表示已经接管，不能留下“默认处理被跳过，替代效果也无人完成”的缺口。

`after_elemental_reaction` 应当位于这次反应效果全部处理之后，反应中创建的实体也可以参与这一时机；由伤害引发时，它在伤害后通知之前。无反应的附着不应仅因为修改了附着就发送反应通知。

当前默认反应后果及部分伤害侧反应加成尚未完成，见[源码问题清单](../reference_scope.md)。这说明实现尚有缺口，不改变默认处理或接管者应当完成整次反应的责任。

旧文把 `reacted_aura` 称作“参与反应的旧 aura”，不能据此把它收窄成仅包含被反应消耗的那部分附着；当前语义是反应开始前的完整目标附着快照。

## 伤害后的击倒处理

原约定在伤害后响应完成后，才为生命值为零的角色安排击倒处理。`deal_damage` 目前在伤害后响应完成后检查双方存活情况，但尚未接入 `character_will_be_defeated` 与 `character_defeated` 的完整流程。

终局检查由完整领域结算承担，不能要求定义源另接一条通用检查指令，见[指令设计备忘](../instructions.md#结算边界)。防止击倒、复活以及何时请求出战选择的规则见[击倒与延迟出战选择](entity_events.md#击倒与延迟出战选择)。

## 治疗完成量

治疗完成通知 `healed` 应记录实际恢复的生命值，不能把治疗前提出的数额直接当作最终恢复量。当前治疗事件类型已声明，核心治疗流程尚待补全；这一区分仍是实现应遵守的要求。
