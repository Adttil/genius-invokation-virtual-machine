# 费用预览、提交缓存与取消

这里记录行动费用的报价与延迟效果。公开接口见 [action_selection](../../reference/executor/execution_view/action_selection.md) 和 [begin_action](../../reference/definition/commands/begin_action.md)。

## 为什么预览与提交隔离

查看价格不应消耗减费次数或产生持久副作用。费用 handler 修改报价事件，并通过 `handle_context::invoke` 提交后续效果及其全部初始输入；执行器在报价期间只缓存它们，最终只执行所选候选的效果。

同一报价中的全部 handler 读取不变的 table，前一 handler 只通过费用事件影响后一 handler。报价响应不得使用随机数，调用随机源属于文档约定的未定义行为，不增加检查机制。其内部随机函数与对局随机源隔离。

这些约束保证提交时不必重跑报价，也不必复制 table 来模拟支付效果。后续支付程序造成的持久变化不会反过来改变本次已确定的报价与输入。

## 每个候选只计算一次

一个行动窗口内，每个候选最多调用一次计算接口。上层自行保证，不保存“已经报价”标志，也不进行运行期重复检查。完整报价之后，读取接口可以反复查询已有结果。

`calculate_switch_cost` 从默认切换费用开始；`calculate_card_cost` 与 `calculate_skill_cost` 分别读取已保存的静态初始费用，再调用对应费用响应。目标选择与支付检查不影响这项计算次数约定。

采用已计算费用的提交重载不再报价；带定义库与 table 的重载只用于尚未计算的候选，同步完成首次计算后填写选择。下一次 `step` 只执行已确认结果。

报价不提供异常回滚。失败候选可能留下部分费用和缓存，不能在当前窗口读取、检查、采用或重算。上层不得把异常后留下的部分状态当成完整结果。

## 缓存布局

仍采用 C 个候选与 H 个响应者组成的 C×H 矩阵。实际报价时写入对应行，建立现场时不预先清零整张矩阵。无后续调用的响应也写入空缓存项，保留响应顺序及对应关系。

入口、参数块相对位置和实际字节长度分别保存在三个同形状的数组中，由行动实现按候选与响应者定位。全部参数块追加在行动帧尾部的子栈中；这里只追加真实发生的调用输入，不按定义源中所有程序的最大长度预留空间。

收集报价时，费用响应通过 `context.invoke(substack_t{}, entry, inputs...)` 选择向尾部子栈写入的重载。它只追加输入并返回入口，不准备返回位置或进入程序；行动实现自行记录响应前后的栈长度增量，计算并保存参数块的位置和长度。`program_invoker` 不保存缓存项，也不认识候选矩阵。

公开响应签名仍是四参数形式，最后接收具体的 `handle_context&`。写入主栈或尾部子栈由是否提供首参数 `substack_t{}` 的重载在编译期选择，`handle_context` 和 `program_invoker` 不保存写入模式标志。费用响应提交时必须使用子栈重载，普通响应使用普通重载；由定义源遵守，不增加运行期检查。

每段输入按对应命令的消费顺序反向保存。每个 handler 的输入独立，不能借用会被后续 handler 修改的费用事件。输入要使用的完整响应者身份仍由定义源明确填写；固定效果的相对玩家则在缓存程序实际执行时，以该响应者所属玩家为本方。报价与 handler 调用不改变 `self_player`，也不临时写牌桌后再恢复。

由于每个候选只报价一次，不需要旧参数块回收、空闲链表、区间压缩或重复报价标记。缓存总量由本窗口实际计算的候选及其调用输入决定。

## 按原顺序执行缓存调用

收集报价只记录调用，不需要返回记录。确认行动时在整个行动帧上方压入独立的 `response_return`，保存外层本方和返回位置，然后按先前响应顺序回放所选行；所有缓存程序共用这一记录。每次先为当前调用的参数块预留必要容量，再根据相对位置取得缓存字节 span，通过内部复制接口复制到执行区域，并在进入程序时建立对应响应者的本方；其程序依次消费输入，返回时恢复外层本方但不弹出返回记录，随后继续下一项。全部效果执行完后由行动流程弹出记录，再开始实际支付。

不反转整片缓存，也不执行未选候选的效果。相对位置在栈扩容和整个执行器复制后保持有效。每个实际提交的调用会有一次参数块复制，这换取了缓存与运行输入互不覆盖，并避免为任意类型参数建立独立分配器。预留容量发生在取得字节 span 之前，后续复制不再因这次提交移动它借用的源数据；缓存回放复用已经验证的帧，不走公开输入对象转换和检查。缓存子栈在确认后只读，允许在其上方保存返回位置和当前执行输入。

提交不重新调用费用 handler，不重新采样响应者或检查先前响应者有效性。程序使用报价时已经提交的输入；命令自身的目标前提仍由定义源保证，不能把普通广播跳过已失效实体的规则套到缓存执行上。

## 缓存输入的快照与执行前提

每个费用 handler 提交的是报价时输入的快照；同一候选的其他 handler 也读取同一份未改变的 table。回放时前一个缓存程序及其嵌套响应可能改变状态或删除实体，后一个程序的输入不会因此重算。定义源必须保证每条命令实际执行时仍满足目标有效性、资源需求等前提，不能仅以报价时满足这些条件为依据。

消耗状态层数或次数时，可以提交 `modify_*_state` 的负增量，使命令从执行时现值扣除，避免绝对赋值覆盖前一个效果已经做出的修改。但饱和到零只定义数值计算，不保证本次减费仍有足够资源，也不保证目标仍存在；前一个缓存程序可能已经耗尽并删除它。这些条件仍须由费用规则及其程序共同保证。一次缓存程序把资源消耗排在自身首条，也不能替代对先前缓存程序影响的检查。

缓存输入仍可以有意保留报价时的数值。这里不要求每个从 table 派生的参数都由第一条命令消费，也不重新报价；要求的是所选程序按既定快照执行后仍符合费用规则。普通即时响应中先消耗资源再进入其他效果的建议见[实体事件](entity_events.md#响应快照与执行前提)。

## 支付检查与提交

支付检查独立读取已完成的报价和 table，依次检查骰子是否匹配、骰子是否付得起，再检查出战角色的充能类型与数量。每种行动保留自己的结果枚举；提交接口不会自动执行检查。

卡牌与技能的目标检查也独立进行。目标以 span 提供，最多采用前两个 ID，允许空选择；定义查询分步返回无效、必须继续、可以完成也可以继续、已完成不可继续。不额外保存检查进度。

最终选择用 variant 保存切换、出牌、技能和结束声明及其对应数据，不记录“未选择”。调用方须先提供合法输入再继续 `step`。

所选费用效果先执行，随后扣除支付骰子与支付阶段出战角色的充能，两项扣除完成后依次广播非零骰子支付的 `dice_removed` 和非零充能支付的 `energy_changed`。费用已经确定，不通过 `changing_energy` 重新报价。充能不需要上层另选支付对象或单位。

出牌先标记所选手牌删除，使其离开手牌遍历和普通广播，但在清理前仍可通过原 ID 读取信息。随后执行缓存、支付、`card_will_be_played`；未反制时执行本牌的 `card_effect`，最后无论是否反制均广播 `card_played`。反制只取消原效果。

技能支付后广播 `skill_will_be_used`，未取消时执行所选技能的 `skill_effect`，最后均广播 `skill_used`。技能不会因使用而离场。

## 取消与引用生命周期

上层只查看候选、改选其他候选或选择结束回合，都不会执行未提交效果。行动窗口结束时整体丢弃候选及其参数子栈；进入提交后的副作用不提供自动回滚。

报价任一新候选都可能扩容，因此之前通过费用接口取得的引用可能失效。view 本身能重新定位，但其成员返回的具体引用不是稳定地址，需要通过 view 再次获取。推进、重建现场或终局也会结束原引用的有效期。

旧 `calculating_card_payment`、`calculating_skill_payment`、`calculating_switch_payment` 的 table payment 槽位方案见[历史 payment 设计](resource_events.md)，不能代替当前的调用输入缓存。
