# 费用预览、提交缓存与取消

这里记录行动费用的报价与延迟效果。公开接口见 [action_selection](../../reference/executor/execution_view/action_selection.md) 和 [begin_action](../../reference/definition/commands/begin_action.md)。

## 为什么预览与提交隔离

查看价格不应消耗减费次数或产生持久副作用。费用 handler 修改报价事件，并通过 `handle_context::invoke` 提交后续效果及其全部初始输入；执行器在报价期间只缓存它们，最终只执行所选候选的效果。

同一报价中的全部 handler 读取不变的 table，前一 handler 只通过费用事件影响后一 handler。报价响应不得使用随机数，调用随机源属于文档约定的未定义行为，不增加检查机制。其内部随机函数与对局随机源隔离。

这些约束保证提交时不必重跑报价，也不必复制 table 来模拟支付效果。后续支付程序造成的持久变化不会反过来改变本次已确定的报价与输入。

## 按完整选择报价

一个行动窗口内，同一操作及完整目标组合最多调用一次计算接口。同一手牌、技能或特技可以针对不同目标分别报价。Release 由上层保存对应标识，不搜索去重；Debug 检查重复和未完成报价。完整报价之后，读取接口通过标识反复查询已有结果。

`calculate_switch_cost` 从默认切换费用开始；卡牌、技能和特技分别从对应初始费用开始，再调用费用响应。后三种报价接收完整目标 span，在事件中保存两个只读目标槽；`std::monostate` 表示空槽，首个空槽终止目标序列，不额外保存目标数量。分步目标检查继续独立提供，Debug 报价会按合法前缀检查完整选择。

报价返回对应的 `switch_cost_id`、`card_cost_id`、`skill_cost_id` 或 `technique_cost_id`。读取、支付检查及 `_with_cached_cost` 提交接口使用标识；缓存提交不另收来源或目标。直接行动接口只用于尚未计算的操作及目标组合，同步完成首次报价后提交。二者均立即推进，只执行已确认结果。

报价不提供异常回滚。失败候选可能留下部分费用和缓存，不能在当前窗口读取、检查、采用或重算。上层不得把异常后留下的部分状态当成完整结果。

## 缓存布局

行动窗口保留各类候选 ID、按默认顺序收集的费用响应者列表，以及尾部缓存子栈。没有候选与响应者的二维矩阵。每次实际报价只追加本次的完整费用事件及 H 个程序描述；未查询的目标组合不分配报价记录。

程序描述将入口、本方玩家、参数块相对位置和字节长度放在一起。报价记录保存费用事件及描述数组的位置和数量，不透明标识直接定位记录；读取报价和第几个程序均不遍历先前报价。全部记录和参数块追加在同一缓存子栈中，窗口结束时整体回收。只有 Debug 使用附加记录链接检查重复报价。

收集报价时，费用响应通过 `context.invoke(entry, inputs...)` 选择向尾部子栈写入的重载。它只追加输入并返回入口，不准备返回位置或进入程序；行动实现记录输入范围。`program_invoker` 不保存报价记录，也不解释付款。

响应类别由事件的 `static constexpr event_category category` 指定。普通和立即响应接收编号，预览响应没有编号。`handle_context<TEntity, Category>` 仅接受同类别效果，统一通过 `invoke(entry, inputs...)` 提交；预览上下文自动缓存输入，且没有随机源接口。类别在编译期确定，不保留运行期方式字段。

每段输入按对应命令的消费顺序反向保存。每个 handler 的输入独立，不能借用会被后续 handler 修改的费用事件。输入要使用的完整响应者身份仍由定义源明确填写；固定效果的相对玩家则在缓存程序实际执行时，以该响应者所属玩家为本方。报价与 handler 调用不改变 `self_player`，也不临时写牌桌后再恢复。

由于每个操作和目标组合只报价一次，不需要旧参数块回收、空闲链表或区间压缩。缓存总量由本窗口实际报价的组合及其调用输入决定。

## 按原顺序执行缓存调用

收集报价只记录调用，不需要返回记录。确认行动后，回放游标和锁定选择保存在行动帧中，调用者保存自己的续点；每次实际程序调用另压入返回帧，并建立独立结算域。程序主体及其全部派生结算完成后，恢复本方、弹出本次返回帧，再继续下一个缓存程序。返回编号忽略，不再调用费用 handle。全部效果完成后开始实际支付。

不反转整片缓存，也不执行未选候选的效果。相对位置在栈扩容和整个执行器复制后保持有效。每个实际提交的调用会有一次参数块复制，这换取了缓存与运行输入互不覆盖，并避免为任意类型参数建立独立分配器。预留容量发生在取得字节 span 之前，后续复制不再因这次提交移动它借用的源数据；缓存回放复用已经验证的帧，不走公开输入对象转换和检查。缓存子栈在确认后只读，允许在其上方保存返回位置和当前执行输入。

提交不重新调用费用 handler，不重新采样响应者或检查先前响应者有效性。程序使用报价时已经提交的输入；命令自身的目标前提仍由定义源保证，不能把普通广播跳过已失效实体的规则套到缓存执行上。

## 缓存输入的快照与执行前提

每个费用 handler 提交的是报价时输入的快照；同一候选的其他 handler 也读取同一份未改变的 table。回放时前一个缓存程序及其嵌套响应可能改变状态或删除实体，后一个程序的输入不会因此重算。定义源必须保证每条命令实际执行时仍满足目标有效性、资源需求等前提，不能仅以报价时满足这些条件为依据。

消耗状态层数或次数时，可以提交 `modify_*_state` 的负增量，使命令从执行时现值扣除，避免绝对赋值覆盖前一个效果已经做出的修改。但饱和到零只定义数值计算，不保证本次减费仍有足够资源，也不保证目标仍存在；前一个缓存程序可能已经耗尽并删除它。这些条件仍须由费用规则及其程序共同保证。一次缓存程序把资源消耗排在自身首条，也不能替代对先前缓存程序影响的检查。

缓存输入仍可以有意保留报价时的数值。这里不要求每个从 table 派生的参数都由第一条命令消费，也不重新报价；要求的是所选程序按既定快照执行后仍符合费用规则。普通即时响应中先消耗资源再进入其他效果的建议见[实体事件](entity_events.md#响应快照与执行前提)。

## 支付检查与提交

支付检查独立读取已完成的报价和 table，依次检查骰子是否匹配、骰子是否付得起，再检查出战角色的充能类型与数量。每种行动保留自己的结果枚举；Debug 提交自动执行检查，Release 不执行。

卡牌与技能的目标检查也独立进行。目标以 span 提供，最多采用前两个 ID，允许空选择；定义查询分步返回无效、必须继续、可以完成也可以继续、已完成不可继续。不额外保存检查进度。

最终选择用 variant 保存切换、出牌、技能和结束声明及其对应数据，不记录“未选择”。输入接口填写选择后立即进入内部推进循环；公开接口不存在独立 `step`。

确认时锁定原选骰色及数量、原付费角色、行动来源和目标，以及支付前确定的重击等标记。费用程序可以暂停，恢复后继续其完整结算；若已判终局，则停止付款和实际行动。

每色实际付款为 `min(原选数量, 当前数量)`，各色独立，不拿其他颜色或万能骰补足。费用效果新增的同色骰可以被扣到，不追踪具体骰子身份。充能从锁定的原付费角色饱和扣除，费用效果切换出战不会改换付费对象。费用已经确定，不通过 `changing_energy` 重新报价。

`dice_removed` 和 `energy_changed` 报告实际变化，零变化不登记；付款记录归入实际行动段，与行动通知一起结算。扣款前不提前处理付款通知。

出牌先标记所选手牌删除，使其离开手牌遍历和普通广播，但在清理前仍可通过原 ID 读取信息。随后执行缓存、支付、`card_will_be_played`；未反制时执行本牌的 `this_card_play`，最后无论是否反制均广播 `card_played`。反制只取消原效果。

技能支付后广播 `skill_will_be_used`，未取消时执行所选技能的 `this_skill_use`，最后均广播 `skill_used`。技能不会因使用而离场。

## 取消与引用生命周期

上层只查看候选、改选其他候选或选择结束回合，都不会执行未提交效果。行动窗口结束时整体丢弃候选及其参数子栈；进入提交后的副作用不提供自动回滚。

报价任一新候选都可能扩容，因此之前通过费用接口取得的引用可能失效。view 本身能重新定位，但其成员返回的具体引用不是稳定地址，需要通过 view 再次获取。推进、重建现场或终局也会结束原引用的有效期。

旧 `calculating_card_payment`、`calculating_skill_payment`、`calculating_switch_payment` 及订阅声明已删除；旧 table payment 槽位方案只作为[历史 payment 设计](resource_events.md)保留。
