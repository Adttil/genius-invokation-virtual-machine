# 初始化、击倒与实体身份

这里保留初始化同步完成的取舍、击倒后的输入时机，以及离场身份和计数器的规则边界。成员声明见[事件 reference](../../reference/definition/events.md)。

## 初始化刻意同步完成

角色初始状态只涉及角色自己的编译后定义，通过空参数类型的 [`character_initial_state`](../../reference/definition/queries/character_initial_state.md) 提供。结果在编译定义库时求出并保存，初始化时直接写入角色。

初始化不再借用响应接口，也不接受牌桌、随机源或后续效果入口。这个选择同时适用于单个角色入场和已装入牌桌的角色批量初始化；需要依赖当前对局状态的额外效果应由相应事件和命令表达。

## 击倒与延迟出战选择

防止击倒或复活的效果应在真正写入击倒状态前介入；后续响应能够观察到先前响应已经阻止击倒。效果自身的消耗通过响应程序完成。伤害后再进入击倒处理的时机见[伤害与元素反应](damage_and_element_events.md#伤害后的击倒处理)。

原设计明确选择延迟请求替补出战：出战角色被击倒不会立即使系统等待输入，真正需要出战角色的后续指令才请求选择。当前完整击倒、复活和延迟选择流程尚未接入，`begin_action` 仍要求已有出战角色；后续实现需要落实这项分工。

## 离场前后与历史身份

离场前可以读取实体定义和状态，并通知实体自身；离场后的实体已失效，不再参加通常的遍历和广播，但在 cleanup 前仍可按旧 ID 读取定义、状态及归属。若需要实体自身执行离场效果，负责离场的领域操作应在失效前通知或提前安排。

这项边界也适用于弃牌、打牌完成和调和完成所携带的原牌 ID。cleanup 才回收和压缩实体存储，跨 cleanup 沿用 ID 的限制仍然适用。

## 添加、替换与移除附件

`add_attachment` 消费响应明确提交的 `attachment_addition`。输入包含目标、定义和初始状态，不需要读取原响应事件。装备类别由 attachment 定义的 `weapon`、`artifact`、`talent`、`technique` 标签决定，这些类别标签互斥；没有类别标签时是普通附件。固定版本 `add_attachment_to_active_character` 在执行时定位指定一方的出战角色，再进入相同结算阶段。

普通附件独立追加。同类装备已有占用者时，先采样并完成旧实体的 `entity_will_leave`，再删除旧实体，随后采样并完成 `entity_left`；最后创建新装备并广播 `attachment_added`。删除只标记失效，保留旧信息，并清除仍指向自身的装备索引。

离场前响应可能提前移除或替换旧装备，此时外层流程不重复发送旧实体的离场完成通知。离场后响应也可能安装其他装备，因此添加流程在恢复时重新读取该类别，直到无占用者才安装本次装备。`remove_attachment` 采用相同的离场通知顺序，只移除明确指定的实体，不追踪后续替代者。

装备索引是角色数据中的固定数组，附件仍按加入顺序追加到原容器。附件数据只保存定义与失效标记、状态，不重复保存装备类别；添加时从定义库查询标签派生的类别，并更新角色的对应索引。删除时清除指向自身的装备索引；cleanup 按原顺序压缩附件，同时把装备索引从旧位置更新到新位置，不需要重新分类或访问定义库。公开的 `attachments()` 仍按加入顺序遍历；默认广播先通过角色装备接口访问武器、圣遗物、天赋、特技，再遍历非装备附件。类别来自定义标签，不对外提供独立的类别输入；特技主动行动机制尚未接入。

定义库仅用固定 `array` 保存装备类别标签的 ID，查询分类时读取定义已有的标签位，不再为每个 attachment 定义保存一份分类缓存。数组长度取 `equipment_type::none` 的底层值；有效类别从零开始连续编号，`none` 放在最后。角色视图使用 `has(type)` 与 `get(type)` 访问指定类别，普通附属实体不适用这两个接口。

table 内部的角色 handle 保留两个添加重载：`add(definition, state)` 只添加普通附件，`add(definition, state, equipment_type)` 只添加指定类别的装备。装备重载要求传入有效装备类别，不能传入 `none`；只在 debug 下检查此条件。table 不自行查询定义标签，执行添加命令时由 executor 从定义库取得类别，再调用相应重载。

## 完整计数器不等于单一剩余次数

带计数实体的 `count` 是完整的 `std::uint32_t`；定义可以自行解释其中的位布局。`entity_count_changed` 记录替换前后的完整值，不能把“次数或层数”的常见用途收窄成只允许单一计数。

零值也不自动表示离场。定义可以按自己的规则，在零值或其他条件下安排离场效果；框架不能统一把 `count == 0` 当作自动销毁条件。不同领域指令对计数的解释和通知责任须分别确定：例如现有 `reduce_combat_status_count` 将出战状态的计数作为可消耗次数，直接减少计数，不自动产生 `entity_count_changed` 或安排离场。
