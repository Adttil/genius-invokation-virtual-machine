# 初始化、击倒与实体身份

这里保留初始化同步完成的取舍、击倒后的输入时机，以及实体生成、状态修改和离场身份的规则边界。成员声明见[事件 reference](../../reference/definition/events.md)。

## 初始化刻意同步完成

角色初始状态只涉及角色自己的编译后定义，通过空参数类型的 [`character_initial_state`](../../reference/definition/queries/character_initial_state.md) 提供。结果在编译定义库时求出并保存，初始化时直接写入角色。

初始化不再借用响应接口，也不接受牌桌、随机源或后续效果入口。这个选择同时适用于单个角色入场和已装入牌桌的角色批量初始化；需要依赖当前对局状态的额外效果应由相应事件和命令表达。

## 击倒与延迟出战选择

每次扣血使生命降至零后立即进入击倒处理，先于元素反应及伤害后响应。当前先判定终局；对局继续时才删除角色全部 attachment、清空充能。濒死复活广播尚未接入；后续应在终局判定与清理前广播，使角色自身 attachment 能够阻止击倒。广播返回后根据生命是否恢复决定是否击倒；复活失败时仍先判定终局，终局直接停止，只有继续对局才清理。具体边界见[伤害与元素反应](damage_and_element_events.md#扣血后的击倒处理)。

原设计明确选择延迟请求替补出战：出战角色被击倒不会立即使系统等待输入，真正需要出战角色的后续指令才请求选择。当前已处理击倒时的 attachment 与充能清理，濒死复活、击倒通知和延迟选择流程尚未接入，`begin_action` 仍要求已有出战角色；后续实现需要落实这项分工。

## 离场通知与历史身份

实体移除先标记失效，再根据类别全场广播 `summon_removed`、`combat_status_removed` 或 `attachment_removed`，不再提供离场前事件。三种事件分别以 `const summon_id summon`、`const combat_status_id status` 和 `const attachment_id attachment` 保存已删除实体的身份。离场后的实体不再参加通常的遍历和广播，但在 cleanup 前仍可按旧 ID 读取定义、状态及归属。删除后通知面向仍有效的响应者，已离场的实体自身不会响应；需要由自身执行的效果，应由导致离场的程序在删除前安排。

这项边界也适用于弃牌、打牌完成和调和完成所携带的原牌 ID。cleanup 才回收和压缩实体存储，跨 cleanup 沿用 ID 的限制仍然适用。

## 添加、替换与移除附件

默认构造的 `add_attachment{}` 消费响应明确提交的 `attachment_addition`，由输入提供目标、定义和初始状态。显式提供 `definition` 时使用固定参数，不消费输入，在执行时定位 `player` 指定一方的出战角色，再进入相同结算阶段。两种方式的初始状态都逐字段限制到定义上限，参数来源在编译时确定，不读取原响应事件。装备类别由 attachment 定义的 `weapon`、`artifact`、`talent`、`technique` 标签决定，这些类别标签互斥；没有类别标签时是普通附件。

普通附件独立追加。同类装备已有占用者时，先删除旧实体，再采样并完成 `attachment_removed`；最后创建新装备，不发送添加完成事件。删除只标记失效，保留旧信息，并清除仍指向自身的装备索引。

离场后响应可能安装其他装备，因此添加流程在恢复时重新读取该类别，直到无占用者才安装本次装备。`remove_attachment` 同样先删除再通知，只移除明确指定的实体，不追踪后续替代者。

装备索引是角色数据中的固定数组，附件仍按加入顺序追加到原容器。附件数据只保存定义与失效标记、状态，不重复保存装备类别；添加时从定义库查询标签派生的类别，并更新角色的对应索引。删除时清除指向自身的装备索引；cleanup 按原顺序压缩附件，同时把装备索引从旧位置更新到新位置，不需要重新分类或访问定义库。公开的 `attachments()` 仍按加入顺序遍历；默认广播先通过角色装备接口访问武器、圣遗物、天赋、特技，再遍历非装备附件。类别来自定义标签，不对外提供独立的类别输入；特技主动行动机制尚未接入。

定义库仅用固定 `array` 保存装备类别标签的 ID，查询分类时读取定义已有的标签位，不再为每个 attachment 定义保存一份分类缓存。数组长度取 `equipment_type::none` 的底层值；有效类别从零开始连续编号，`none` 放在最后。角色视图使用 `has(type)` 与 `get(type)` 访问指定类别，普通附属实体不适用这两个接口。

table 内部的角色 handle 保留两个添加重载：`add(definition, state)` 只添加普通附件，`add(definition, state, equipment_type)` 只添加指定类别的装备。装备重载要求传入有效装备类别，不能传入 `none`；只在 debug 下检查此条件。table 不自行查询定义标签，执行添加命令时由 executor 从定义库取得类别，再调用相应重载。

## 生成与直接添加

召唤、生成出战状态和附着分别使用 `summon`、`generate_combat_status` 和 `attach`。它们执行时才查找目标范围的首个有效同定义实体：不存在时按本次输入创建；存在时只调用该实体的重复生成响应，返回的程序决定刷新、叠加、独立添加或删除重建。缺少响应或返回空入口都表示无操作，不再默认追加。只调用首个匹配实体，防止多个副本分别处理同一请求。

| 命令 | 动态输入 | 已有实体的定向通知 |
| --- | --- | --- |
| `summon` | `summoning` | `resummoning` |
| `generate_combat_status` | `combat_status_generation` | `combat_status_regeneration` |
| `attach` | `attachment_application` | `attachment_reapplication` |

`add_summon`、`add_combat_status` 和 `add_attachment` 直接添加，不进行同定义实体判断，避免重复生成响应中的追加再次进入生成处理。新建实体没有全场的添加完成通知；只有重复生成和自身状态变化使用定向通知，离场后按类别全场广播 `summon_removed`、`combat_status_removed` 或 `attachment_removed`。

### 状态上限与生成参数

三类定义分别通过 `summon_state_limit`、`combat_status_state_limit` 和 `attachment_state_limit` 提供各字段上限。查询在定义库编译时求值并保存，不再把查询结果解释为初始状态；缺少查询时每个字段的上限都是 `UINT32_MAX`。

生成和直接添加命令都携带本次希望写入的 `state`，固定命令值和动态输入的两个字段均默认 `UINT32_MAX`。执行时逐字段取 `min(输入值, 定义上限)`，再创建或交给已有实体的重复生成响应。因此省略状态相当于采用各字段上限；显式提供较小值可以生成部分层数或次数。`UINT32_MAX` 是普通数值，没有“未指定”的哨兵含义，也不触发另一套初始化协议。

创建新召唤物要求裁剪后的 `usages > 0`；这是调用前提，不把零次数的创建解释为无操作。

固定模式由显式 `definition` 选择，不消费响应输入；动态模式消费对应输入。其中附件的固定模式在执行时定位指定一方的出战角色，动态模式明确指定目标角色。

## 状态修改与耗尽

召唤物的 state 明确区分效果量 `value` 与可用次数 `usages`。状态写入后可用次数为零时，执行器立即删除并广播 `summon_removed`，不再发送 `summon_state_changed`，无需定义提供判零响应。其他修改只向本召唤物发送 `summon_state_changed`。

attachment 与 combat_status 分别记录层数 `count` 和每回合剩余次数 `round_usages`。修改后仅向自身发送相应的 `state_changed`，由定义决定零层数时是否离场；回合次数的重置同样由定义响应回合事件后提交修改命令，执行器不统一重置。

`set_*_state` 以绝对值覆盖状态，逐字段限制到定义上限。`modify_*_state` 接受 `std::int64_t` 增量：召唤物为 `value`、`usages`，两类状态为 `count`、`round_usages`。动态输入分别为 `summon_state_modification`、`combat_status_state_modification` 和 `attachment_state_modification`。相对修改在命令实际执行时读取当前值，再把数学上的“当前值 + 增量”饱和到 `[0, 定义上限]`，避免无符号下溢或加法溢出；零增量保留相应字段。扣层和次数消耗统一用负增量表达，不再提供专用的出战状态扣层命令。

定向通知不收集全场实体，只调用一个 handle。子程序返回后修改命令才结束；实体可能已经被响应删除，因此收尾不继续读取实体。通知的旧值和新值属于本次写入的快照。直接 table state 赋值只属于存储操作，通知由领域命令执行。

## 响应快照与执行前提

handler 根据响应时的牌桌一次性计算整段程序输入，这些输入是快照，不会在后续命令执行前自动重算。绝对赋值会写入该快照；相对修改只保存增量，在执行时以目标最新的状态为基础计算。二者都要求命令实际执行时满足目标有效性等输入前提，相对修改本身不负责重新确认此前决定的效果是否仍应发生。

普通即时响应若先承诺消耗次数、护盾层数等资源，推荐把相应修改放在可能触发其他响应的效果之前。修改命令先写状态再通知，这样重入的响应会看到已经消耗后的资源。例如护盾在伤害响应中决定吸收量后，先提交负的 `count` 增量，再执行依赖这次吸收的其他效果，避免嵌套效果再次使用尚未扣除的层数。

这不是“所有从 table 计算的参数都必须由第一条命令消费”的限制。按规则需要保留响应时数值的伤害、选择结果等可以在后续命令使用；定义源只需保证其快照语义符合效果，并保证实际执行时的输入前提。费用报价还会延迟执行、顺序回放多个缓存调用，其前提需另按[费用提交协议](payment_commit.md#缓存输入的快照与执行前提)保证。
