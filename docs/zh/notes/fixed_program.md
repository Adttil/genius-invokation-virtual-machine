# 固定程序、重入与表达能力

本页保留从动态程序转向固定程序后的表达策略、接口约定与内部连接方式，并说明旧术语和已变化的实现细节。

来源：提交 `b3d6c50` 中的 `docs/zh/old/fixed-program-design.md`。保留固定程序的设计约束、表达策略和历史取舍。

定义源集（卡牌、角色、状态等规则定义）和游戏流程规则共同编译为一个游戏规则程序。executor 保存当前执行位置和结算中的临时状态，按照这个程序持续推进游戏。

“固定”表示程序中的规则步骤在对局开始前已经确定。运行时可以读取状态、修改事件、选择分支和执行动态数量的领域操作，但不会临时生成一段新的指令序列。

下文保存固定程序模型形成时的设计约束与表达策略。具体字段的公开说明见 reference；具体指令的栈布局直接查阅源码，跨指令的调用与广播机制见[事件分派](event_dispatch.md)。

## 基本约束

- 定义源和游戏流程只能组合、配置核心给定的公开指令来描述游戏规则程序，不能提供核心之外的指令类型。
- 指令保存预先确定的操作参数，自身不会在执行过程中改变。
- 对局中持续存在的规则状态保存在 table；当前执行位置和临时结算状态保存在 executor。
- handler 只能选择已经编译的响应程序，不能在运行时构造新的程序。
- 公开指令所负责的领域结算结束后，应当恢复开始该结算时的栈形状；进入终局时旧帧被逻辑废弃，不要求沿调用链清理。

各段程序在编译结果中如何连接不属于公开接口。公开指令用于描述规则；上层通过执行现场观察对局，不再取得当前指令或执行位置。

## 程序入口与 Context

`program_entry<Context>` 表示一段响应程序的入口。旧文以“`Context` 规定进入该程序时可用的栈 ABI”解释入口为何不能互换；当前公开解释是该程序段所处的事件语境和允许进行的操作，内部再把它映射到相应数据布局。不同 Context 的入口仍不能互换。例如，历史记录中使用过：

```cpp
program_entry<damage_effect>
program_entry<onpay_context<cost_of_switch>>
```

通常直接以事件类型作为 Context；费用事件的效果通过 `onpay_context<CostEvent>` 映射。这里保留这一类型映射的实现名称，不把费用事件另分为一种事件类别；定义作者可用 `handler_program_context_t<Event>` 与 `handler_program_entry_t<Event>` 表达映射。初始化程序和回合程序不依赖调用者的 Context。

空入口表示“没有响应子程序”。handler 返回空入口时，调用方不会进入其他程序；handler 对 event 已经完成的修改仍然保留。空入口的数值表示不是公开接口。

终局由公开的 `end_game{ .result = ... }` 指令表达，它不依赖 Context，可以编入任意相容的程序。`program_entry<Context>` 只区分空入口与程序入口，不再提供三种结果工厂。执行终局操作后，推进统一返回 `finished`，由终局视图读取结果；旧结算现场不再有效。

## 游戏流程与响应程序

游戏流程表示这样的整体运行语义：先执行一次初始化程序，再反复执行回合程序，直到相关领域指令触发对局结束。编译调用方必须提供这两段公开指令序列。

handler 返回的响应程序是一段会回到原结算过程的子程序。响应完成后，触发它的事件广播或领域指令继续执行。响应期间的内部栈布局见 [指令、栈与事件系统](event_dispatch.md)。

定义响应、onpay 响应和游戏流程使用同一套公开指令描述。内部执行位置与流程之间的连接不属于上层观察协议。

## 指令与 Context

具体指令通过 `context_type` 声明自己是否依赖调用者的 Context：

- 声明 `using context_type = void` 的指令不读取调用者 Context，可以用于任意程序段。
- 声明 `using context_type = E` 的指令依赖 `E` 所表示的事件语境，只能用于 `E` 程序段。旧文将这种限制称为“依赖 `E` 的栈 ABI”；它不表示在同一段源程序里把事件生产指令与消费指令前后拼接。
- 没有 `context_type` 的类型缺少静态 Context 信息，不能通过公开程序边界的兼容性检查。

当前一个依赖 Context 的指令只对应一种 Context。若一项操作需要用于多个 Context，其公开语义就不应依赖某一种事件的栈布局。

`any_instruction_for<E>` 是面向定义源的同构指令值。它在构造时检查指令与 `E` 是否兼容，因此动态来源也可以为特定 Context 返回统一类型的 range。`any_instruction_for<void>` 表示无 Context 依赖的同构指令值。统一元素类型用于容纳核心公开指令，不提供注册新指令种类的能力。

无 Context 依赖的具体指令与已经擦除的包装需要区分。具有 `context_type = void` 的具体指令可以加入事件程序；但当前把已有 `any_instruction_for<void>` 转装成 `any_instruction_for<E>` 时，构造体会按整个包装的尺寸再次做 64 字节检查。已用独立编译核对，该转换因 `72 <= 64` 不成立而失败。context 相容性成立不等于当前擦除包装已经实现这种跨 Context 转装；这是后续实现应单独处理的缺口。

指令集合的约定始终是：

> 公开指令集由核心统一定义，目前仍可随规则能力继续补全。拓展者可以组合和配置这些指令，但不能提供核心之外的指令类型。

`instruction_compatible_with` 检查 context 相容性，`any_instruction_for` 检查尺寸、对齐、平凡复制/析构等要求，内部擦除对象负责分派实际执行。这些模板没有静态检查类型是否属于核心指令集；能通过模板检查不等于符合公开接口约定。核心之外的类型即使能够编译，也不是定义源或游戏流程可以使用的指令。这项限制不以是否增加静态检查为前提，也不是尚待决定的扩展边界。指令执行、重入和栈状态的通用协议见[事件与执行协议](event_dispatch.md)。

## Handler 与响应

handler 是定义提供的 C++ 响应函数。它可以读取 definition data、自身实体、只读 table 和本次随机输入，并直接修改当前 event。需要修改持久 table 时，handler 返回包含相应效果的程序入口，由公开指令完成修改。

普通 handler 返回 `program_entry<Event>`：

- 返回空入口，只保留对 event 的修改；
- 返回非空入口，执行相应响应程序后继续原结算；程序也可以执行 `end_game`，此时结束对局并废弃旧现场，不再返回原结算。

费用预览与确认后的效果提交分离。旧文称后者为“支付后效果”；当前实际顺序是玩家确认行动后先执行全部 onpay，再扣除提交的骰子并广播资源变化，不能把旧称理解为扣款之后才执行。费用 handler 修改费用事件，并返回 `program_entry<onpay_context<CostEvent>>`。onpay 程序只依赖自身 handler 和 `cost_effect_argument<CostEvent>`，不依赖费用计算时的事件工作区。选择理由及缓存约束见[费用预览与提交](event_dispatch/payment_commit.md)。

## 表达能力

固定程序限制的是运行时生成任意新指令序列，而不是规则的计算能力。

### 固定效果

“对敌方出战角色造成 2 点物理伤害”和“对敌方下一个角色造成 2 点物理伤害”可以由不同的公开指令或不同的指令参数表达。它们都是在编译规则时已经确定的规则步骤。

### 动态数量

一次效果的循环次数、目标数量或消耗数量可以由单条领域指令在执行时读取 event、stack 或 table 后处理，不需要把每次循环展开成独立程序段。

例如层数护盾需要取当前层数与最多消耗层数的较小值，同时修改伤害事件并消耗实体层数。这应由 `damage_effect` Context 下的领域指令一次完成，而不是为每种可能层数准备不同程序。

### 运行期计算

伤害随层数增加、按已损失生命增伤、按目标状态调整费用等规则，通常由 handler 直接计算并修改 event。依赖事件 Context 的公开指令也可以继续修改 event 或产生持久效果，因此不需要额外的指令表达式语言。

### 条件分支

handler 或领域指令可以根据运行时状态选择不同的固定入口。只要分支集合在定义时已知，并且具有明确、较小的上限，这种方式就足以表达条件流程。

真正需要避免的是为无界运行时数值枚举程序段。遇到这类规则，应当把计算放入 handler、事件修改或单条领域指令，而不是随数值增加入口数量。

### 指令粒度

早期用“完整且可观察的最小领域操作”限制公开指令粒度，目的是避免把公共 C++ 算法的复用变成许多额外分派。现在指令仍描述领域操作，但公开观察边界由 execution_state 单独表达，不再要求指令与观察现场一一对应。公共算法仍可在 C++ 实现中复用，不应仅为组织观察接口就把领域步骤拆成许多内部小指令。

## 定义源程序

定义源在 `compile(...)` 中通过受限编译上下文解析已声明依赖，并以 `add_program<Context>(instructions)` 加入响应程序。该操作立即返回强类型入口；定义源把需要的 issued id、程序入口和其他配置一起放入 `compile(...)` 的返回对象，不存在后续 setter 或补写阶段。

每段指令只需顺序遍历一次。native C++ 定义可以提交异构 tuple 或同构 range；动态 adapter 可以提交 `any_instruction_for<Context>` 的同构 range。编译上下文负责检查指令与 Context 的兼容性，但不向定义源暴露程序存储和连接方式。

初始化程序和回合程序以 `context_type = void` 的公开指令序列提供。完整定义源接口和编译顺序见 [编写定义源](definition_compilation.md)。

## 一次完整执行与一次完整结算

一次内部调用完整、同步地执行当前指令；指令自身没有可变运行时状态。公开 run、step 可以跨过多次完整调用，后者停在具有公开含义的观察或输入现场。某项结算可以让下一执行位置仍为自己，也可以先进入另一段效果并在返回后重入。`stage_t` 保存的是栈上的状态，不是一个被挂起的 C++ 函数执行到一半的程序计数器。

早期动态程序可以通过追加一条相同指令表示再次处理；固定程序改为保留或恢复相同执行位置。两者均不要求一条指令保存自身可变状态。指令在最终离开自己的结算（而非每次重入）时恢复进入前的栈形状；进入终局时旧现场被逻辑废弃是明确例外。

`deal_damage` 与 `absorb_damage_by_count` 不是相邻指令共享 ABI 的例子。伤害结算发出 `damage_effect`，广播进入另一段响应程序，该响应中的抵挡指令依赖伤害事件 context。伤害结算彻底结束后，其 context 已被清理，不能通过在原源程序的下一条放抵挡指令来取得它。

## 程序的内部连接

核对位置：[executor/library.hpp](../../../include/givm/executor/library.hpp)、[executor/executor.hpp](../../../include/givm/executor/executor.hpp)。

当前实现只保留位置 0 的空入口占位，根程序从内部位置 1 开始；不再预装三个特殊终局入口。旧设计以终局位置编码结果、让 definition 构建时安装终局前缀，其动机和热路径取舍保留在[历史稿](history/fixed_program_2026_09_05.md)。如今结果由 executor 的 `end_game` 指令参数携带，definition 无需依赖具体终局实现。

初始化序列在前，回合序列随后，回合末追加指向回合起点的内部跳转。定义源登记的每段响应末尾追加内部返回指令。这里的数值位置和拼接顺序是实现记录，不能据此要求公开 program_entry 与内部位置互换或序列化为相同索引。

进入子程序时压入 `return_info{ return_position }` 与新的 `stage_t{}`，保存的是调用者当前指令的位置。子程序返回后恢复该位置，由调用者根据自己保留的进度继续。执行器在分派下一次内部调用前收束跳转和返回，使它们不成为需要外层额外驱动的步骤；交付观察现场时，保留视图借用的既有现场，不提前按下一条指令的布局解释它。

空入口不能直接交给内部 enter；调用者须先决定是否存在后续效果。终局执行向栈顶压入 game_result，不附带 stage，旧调用链不能继续访问。公开推进只返回 finished，具体结果由终局视图读取。

后续可以考虑由 `add_program` 统一进行程序去重、公共后缀复用或终局后的不可达尾部截断；本轮均未实现。不能因为某段程序尾部写有 `end_game`，就提前选定该结果：前面的伤害、事件响应或其他步骤仍可能先触发不同终局，实际先执行到的终局才决定结果。

## 指令存储的实现约束

[instruction.hpp](../../../include/givm/executor/instruction.hpp) 中的擦除容器保存最多 64 字节、按 `std::max_align_t` 对齐的指令数据，以及提供执行转发的类型信息指针。指令按字节复制；公开擦除入口要求平凡可复制、平凡可析构，并检查尺寸和对齐，具备对应标准库特性时还检查隐式生命周期类型。

内部取指对象借用该数据与类型信息，用函数指针做运行时分派，不依赖虚基类，也没有为每条指令保存一份可变执行状态。公开 execution_view 借用结算现场，与不可变指令数据的借用不同。这些数据结构说明了为何指令参数、运行状态与外部对象生命周期需要分开审查，不是新的跨版本二进制 ABI。

## 取指结果的表示与借用

旧取指文档为避免调用方锁定内部返回类型及其复制能力，曾要求用 `const auto&`、`auto&&` 或 `decltype(auto)` 接收结果，并禁止 `auto` 或 `const auto`。保留这个理由是为了区分“取得观察对象”和“拥有指令数据”：调用方不应仅从接收变量的写法推断所有权。

此前 definition_library::instruction 曾返回可复制的借用对象，因此 reference 示例使用 auto，早期禁止按值接收的要求已不适用。如今取指进一步移入内部，公开观察改用 execution_view；旧取指对象与定义库同寿命的理由不能套用到当前栈现场。执行视图在下一次推进后失效，复制视图也不会复制现场。
