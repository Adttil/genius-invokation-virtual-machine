# 头文件分层与编译后端迁移

本轮迁移将编译后端从用户编译单元中移出，并逐步提供按用途划分的公开聚合头。目标是降低定义源库及上层游戏的编译、分析负担，同时保留运行期的直接 opcode 执行方式。

## 已确定的边界

- 编译及编译前允许类型擦除与动态分派。命令序列在编译入口统一为 `span<const any_command>`；头文件模板负责包装 tuple、range 或不定参数。
- 命令编译同步完成，入口不保留传入序列或命令借用的数据。
- 公开头位于 `include/givm`；只有用户模板实例化或公开内联代码需要的实现细节才随头文件交付。
- 仅构建核心库时需要的头文件就地放在 `src` 的对应模块目录，供 cpp 共享；私有模板及需要内联的工具也可以放在这里。
- 一处 cpp 独占的实现直接留在该 cpp。无需为每个内部函数建立头文件，也不通过包含 cpp 组织实现。
- 第一层必须提供完整可用的源库类型，使定义库的使用方仅包含其公开头并链接库，就能接收、复制、移动和合并返回的源库；前置声明不能替代这一层。
- 核心库与使用方的 `NDEBUG` 定义须一致。现有调试信息影响部分公开类型的布局，不混用调试与发布配置的二进制。

## 分步计划

每步独立验证和提交，不在第一步顺便搬迁全部命令实现。

### 第一步：非模板编译入口与静态库（已完成）

1. `definition_compile_context::add_program` 提供 `span<const any_command>` 入口，保留命令序列包装，并支持不定参数。
2. 初始化程序和回合程序采用相同边界，保留原有泛型序列的使用方式。
3. 将实际命令编译循环、错误收集和调试输入标记生成移入 cpp。
4. 公开具名的 `definition_compile_result`，其中保存 `library` 和 `id_map`。
5. 将 CMake 目标从 `INTERFACE` 改为静态库，保留 `givm::givm` 链接名称；此时实现 cpp 可以继续包含现有命令实现头。
6. 用 Clang 调试构建、单测及跨编译单元的包含和链接验证现有行为。

验证记录：Clang Debug、两路并行构建通过；CTest 共 664 项测试全部通过，其中包含 319 项文档示例。跨编译单元测试覆盖 span、array、vector、tuple、非连续范围、命令子集 variant、不定参数以及两种编译模式。

### 第二步：命令后端与 view 依赖拆分（已完成）

- 各命令的检查、编译、opcode 和调试输入标记生成放在 `src/executor/commands` 的对应私有头中，由 `src/executor/commands.hpp` 聚合；广播实现放在 `src/executor/broadcast.hpp`。`input_marker` 从公开命令头移入对应私有命令头，保留命令之间已有的实际复用关系。
- `check` 的声明和实现均为私有接口，编译时自动执行。命令、输入、错误类型、`error_type` 别名及错误格式化仍公开，由 `compile` 返回结构化诊断。
- 行动选择、投骰选择和重投选择视图所需的类型与工具直接放在各自视图头中，解除对命令实现头的依赖，不额外提取共享头。报价等原有内联路径继续保留。
- 角色目标解析、后端调试校验和程序写入工具分别保存在 `src/executor/character_target.hpp`、`debug_validation.hpp`、`program_writer.hpp`。行动选择的三个目标验证接口仍需使用 `debug_validate_entity`，因此该小型函数直接内联定义在 `views/action_selection.hpp` 中。
- 自动回合推进的内部命令 `round_program_begin`、`round_program_repeat` 及其编译实现统一放在 `src/executor/commands/start_round.hpp`，不进入公开命令集合。
- 公开头不再包含命令编译、opcode 或广播实现。后端通过私有头复用工具，不增加运行期擦除或函数指针分派。

验证记录：Clang Debug、两路并行构建通过；CTest 共 664 项测试全部通过，其中包含 319 项文档示例。行动选择、投骰选择与重投选择的三个视图头分别在仅提供公开 include 路径时通过独立语法检查。未增加友元声明；命令执行函数、报价函数和迁移的帧类型保持原有行为与布局。

### 第三步：完整而轻量的源库接口（待实施）

- 分离源库持有、合并能力与注册具体 C++ 定义源所需的模板。
- 将源库合并、依赖处理和格式化等非模板实现移入 cpp。
- 通过独立编译单元模拟定义源库的公开头、实现 cpp 和使用方，确认使用方只包含源库接口即可实际使用工厂返回值。

### 第四步：公开聚合头（待实施）

聚合头按能力集合划分，而非强制形成单一包含链。暂定入口如下，最终名称在实现本步时确认：

| 聚合头 | 用途 |
| --- | --- |
| `source_library.hpp` | 持有和组合源库闭包 |
| `source.hpp` | 编写并注册定义源 |
| `compile.hpp` | 编译定义源与对局流程 |
| `runtime.hpp` | 使用编译后的规则推进对局 |
| `givm.hpp` | 全部公开能力 |

对应更新跨模块包含规则：通过指定的公开聚合头跨模块访问，并保持依赖单向。游戏运行接口保留定义库查询能力，不因这些查询引入源注册模板或命令编译后端。

## 验证与测量

维持现有单测聚合方式，额外使用少量独立编译单元验证公开头与链接边界。每步使用一种 Clang 构建配置，至少两路并行。迁移前后记录代表性使用方的编译耗时与头文件依赖规模，用实际结果检查分层收益。

### 第一步后的包含基线

按项目内相对包含递归去重统计，标准库头不计入；行数是各文件原始行数之和，不是预处理输出或编译耗时。

| 入口 | 项目头数量 | 原始行数合计 |
| --- | ---: | ---: |
| `definition/source_library.hpp` | 58 | 7766 |
| `definition.hpp` | 112 | 11109 |
| `executor.hpp` | 187 | 25594 |
| `givm.hpp` | 189 | 25970 |

本步建立了非模板链接边界；命令实现头仍由现有公开聚合头包含，包含规模的进一步缩减由后续步骤完成。

### 第二步后的包含规模

沿用上表的统计方式：

| 入口 | 项目头数量 | 原始行数合计 |
| --- | ---: | ---: |
| `definition/source_library.hpp` | 58 | 7766 |
| `definition.hpp` | 112 | 10700 |
| `executor.hpp` | 135 | 16423 |
| `givm.hpp` | 137 | 16799 |

`givm.hpp` 的项目头减少 52 个，原始行数合计减少约 35%。这是包含规模的变化，不代表同等比例的编译耗时或运行期性能变化。源库接口的依赖尚未拆分，留待第三步处理。
