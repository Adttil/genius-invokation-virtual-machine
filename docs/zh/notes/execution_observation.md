# 执行观察与输入

本页保留观察接口与输入接口共同收紧时的设计理由。公开成员、参数和示例见 [executor](../reference/executor/executor.md)、[execution_state](../reference/executor/execution_state.md) 和 [execution_view](../reference/executor/execution_view.md)。

## 领域现场与内部指令

公开命令描述定义源和游戏流程可以组合的规则操作，内部执行函数不再是公开接口。程序位置、取指和临时帧都不用于上层辨认输入。未来可以另外建立规则描述语言，但本次不依赖这项工作。

每次内部调用完整、同步地执行当前 execute 函数。后续恢复由执行位置选择执行入口，运行数据保存在栈中；不保留一个执行到一半的 C++ 调用，也不再通过 stage 二次分派。公开的 step 则推进到下一处有领域含义的观察现场、输入现场或终局，可以跨过多次完整指令执行。

仅比较推进前后的 table 会丢失过程中已经发生又被覆盖的变化；逐条观察指令又把准备、广播推进和清理等内部步骤交给了上层。因此观察边界由领域操作选择，不把指令类型直接作为输出种类，也不要求一条指令始终只产生同一种现场。

一个内部调用至多交付一处观察现场。双方首次出战选择一起生效后只交付一次完成通知，外部直接读取牌桌上的双方结果；不为了逐项播放动画改变规则的批量结算次序。

## 观察现场继续使用栈

观察优先读取结算本来就需要的栈帧和牌桌字段。早期讨论用“极端情况下仍能压栈”说明执行现场的表达能力足够，并不意味着每个可观察操作都需要另建快照。此前为生命、附着、抽牌、实体等广泛增加旧值、新值和专用清理阶段，扩大了观察模式本身的开销，也超过了已经确定的观察需求，因此撤回。

目前的伤害视图直接读取扣血后留下的 `after_damage`。单方切人先准备原有广播帧，在写入新出战角色前交回控制权，视图从原事件读取目标；下一次推进先更新牌桌，再开始调用响应者。原出战角色直接留在牌桌上，无须复制到栈中。双方首次选择仍稍后再弹出原选择帧：先写入双方出战角色并通知，下一次推进才消费原选择并准备双方广播。这些数据原本就要保存，恢复时的执行位置直接指向后续执行函数。初选完成通知本身不再读取这份选择帧；保留帧只服务于后续规则处理。

流程通知不一定需要访问执行器数据。回合数、当前行动方、结束声明标记在 table 上都有明确字段，外部可以定向读取；无须保存前后快照或扫描双方找差异。初选完成时已知双方都设置了出战角色，可以直接读两方；单方切人的现场则直接给出目标角色 ID，据其玩家字段读取牌桌上的原出战角色，不要求外部比较双方 table 才确定谁发生变化。

纯通知仍可由同一个 `view_in<State>()` 取得空对象，使上层保留统一的访问形式；空视图没有指针或其他成员数据。原来的统一视图基类只存栈指针，没有共同的行为需求，却会让纯通知也带上无用状态，因此移除。getter 使用推导返回类型，状态到访问对象的映射可以自由组织；当前以 `execution_view` 模板实现，不把这套模板形式固定为 getter 的返回类型契约。

栈的复用属于内部存储方案。executor 不再提供原始栈访问，即使只读也会使上层依赖完整帧布局；需要公开的信息应由对应 execution_view 表达。utils 中的栈仍可作为独立工具使用。

观察视图借用该现场，不拥有可无限期保留的日志。上层要保存或异步播放时自行复制所需内容。终局结果是单独确定的协议，不能从它需要压栈推导出所有观察都需要新增栈数据。

## 本次确定的观察边界

观察范围仍限于最终伤害、切人、回合开始、行动机会开始、宣布回合结束、进入回合结束处理。双方初选完成与普通单方切人现用不同的枚举表达，分别对应空通知与单方数据视图。这样单方视图不必在每次读取时判别是不是双方初选，也无需保留用于展示的结果数量或数组接口。

普通切人需要让上层同时知道目标和原出战角色，因此停点放在目标已经确定、牌桌尚未改写时。直接设置与主动切换使用同一观察边界；主动切换的 onpay、骰子支付及资源变化响应仍在此之前完成，不能为了观察切人把付款过程推迟到其后。继续推进时先写入目标，再执行变更响应，所以规则响应读取的仍是新的出战角色。`set_active_character` 的目标本就是原出战角色时，继续沿用不报告观察、但照常广播规则事件的行为。

写入前准备原广播帧依赖当前采样工具的一项局部事实：`collect_all_broadcast_targets` 只依据容器遍历、实体有效性和是否有对应 handler 收集目标，不读取出战角色，也不调用 handler。因此把准备帧放在写入前不会改变这次响应者集合。将来若切人广播的目标或顺序依赖出战角色，需要重新审查这个时机；不能据此推导所有事件的采样都与牌桌修改无关。

元素附着、元素反应、效果响应开始、实体与牌区变更暂不提供独立观察。规则仍照常处理这些操作及相应事件；以后增加观察须从实际展示需求与既有现场出发，单独说明代价。

伤害只在最终值已经确定、已扣除生命后报告，读取的是完整伤害值，而非生命值差。例如角色只剩 1 点生命，999 点伤害仍应能显示为 999。伤害是减少生命的唯一手段，保留 `health_reduced` 命名；不为护盾吸收量或计数的原子变化另设停点。

流程通知的重点是交回控制权的先后：回合开始先更新回合数再通知，之后才判定超限；超限终局时回合数自然大于限制。结束声明先标记并通知，之后才处理声明响应；进入回合结束时先通知，之后才切换先手、清除声明标记与处理回合结束响应。这样上层可以先展示阶段，再展示其中的结算，而无需从结算结果反猜发生顺序。

行动机会不能只靠 `active_player` 是否改变来识别。对方已经结束时，当前玩家每完成一次战斗行动，仍会再次获得行动机会，所以仍需通知。快速行动不结束当前机会，不重复通知；费用预览不推进执行器，上层等待玩家决定时保留当前现场。首次机会要等待行动阶段开始响应完成，之后才开始本次 `before_action` 响应；第一方宣布结束后也须先完成声明响应，再通知另一方获得机会。

回合开始的掷骰子归属仍待整理：目标顺序是更新回合数、超限判定、掷骰子、回合开始广播。当前掷骰子仍由独立 `start_dice_roll_phase` 指令安排，现有事件集合也没有对应的回合开始规则事件。本次仅调整已确认的观察边界与回合计数，不把 `round_started` 观察枚举当作规则事件，也不顺带重组掷骰子流程。

## 普通编译与观察编译

最终 `compile` 显式接收 `compile_mode`，编译上下文把模式传给每个 command 的编译函数。`normal` 只保留输入和终局暂停，`observed` 额外保留已约定的领域观察现场。两种模式编译为相同的 `definition_library` 类型，运行时均通过 `step` 推进。

两种模式保留相同的规则、响应顺序与输入语义，但不要求使用相同的指令数量、执行函数、静态参数类型或内部栈布局。观察模式可以添加恢复入口；普通模式可以直接完成对应工作，不必兼容观察专用的恢复位置。

execute 函数指针已由编译选定，运行时不再查找普通/观察函数表。静态参数通过内部上下文成员 `context.instruction_data<N, T>(library)` 以 const 引用读取，参数地址按上下文已有的执行位置和常量偏移计算，不在 context 中保存原 command 对象或其指针。

## 规则事件与外部观察

规则 event 是 handler 可以修改的结算工作区；执行视图只读呈现已约定的观察内容。二者即使涉及同一次变化，也不共享修改权限。

handler 仅修改 event、返回空入口时，不应把该次修改当作一次要展示的效果触发。此前讨论过仅在 step 模式进入非空响应程序时报告触发，并在新 activation 上追加实体身份和观察 stage；这项实现现已随本次范围收紧撤回，普通广播和 onpay 入口都不再为观察压入额外数据。

如果以后恢复效果触发观察，需要重新确认既有调用现场能否直接提供实体身份，以及通知是否应该发生在响应程序执行之前。费用预览只缓存入口，不能等同于已经确认并进入该程序；这一区别仍成立，但不要求当前先实现触发通知。提交缓存本身的语义见[费用预览、提交缓存与取消](event_dispatch/payment_commit.md)。

## 输入与显式前置条件

输入通过视图上的参数式操作填写，不暴露可写输入引用，也不隐式推进。现场类别由最近一次推进返回值确定，操作不再次验证玩家、候选、费用或阶段，不保存能够由调用前提得到的状态。输入后的下一次推进才消费参数。

选择行动的现场使用 `action_selection`。视图以角色 ID 接收切换目标，`calculate_switch_cost` 同步重算费用并返回只读引用，`check_switch_payment` 独立检查已报价目标的支付；两者都不推进执行器。报价接口无需随机源，费用响应中调用随机函数属于未定义行为。`switch_active_character(target, paid)` 采用已报价结果，传入定义库和牌桌的重载则同步重新报价后提交；下一次推进只执行已确认结果。支付检查不生成报价，提交接口也不自动调用检查。缓存及引用约定见[费用预览与提交](event_dispatch/payment_commit.md)。

状态描述已经确定的协议阶段，不编码玩家身份，也不为每个“command、内部恢复点”的组合机械分配一个状态。不同实现位置需要相同的访问操作时可以共用视图；例如单方换牌与开局换牌的第二次输入都已经确定待选玩家，共用 `card_selection`。该玩家来自换牌流程，不一定是 `active_player`。玩家身份和次数继续作为数据，不为把它们塞进枚举而增加指令端分支。

尚未接受任何一方的选择时可以任选一方，首次输入允许指定玩家；接受第一份输入后，另一方已经确定，第二次输入不再开放改写玩家。开局换牌先提供接受“玩家、位集”的视图，再提供固定玩家的换牌视图。出战初选先接受完整角色 ID；剩余一方的视图读取已经接受的第一份选择，只允许填写待选玩家的角色下标。状态直接由原有流程分支确定，视图不再为辨认首份或剩余输入重查内部阶段，也不保存重复标记。

这项收紧保留任意一方先提交的能力。它与骰子重投的协议不同：重投时任意仍有机会的玩家都可提交，默认玩家只是建议；玩家和剩余次数不拆成新的状态。不能把首次换牌或出战选择的阶段划分套用到重投上。

输入对象不额外记录“已经填写”的标志，调用方须根据当前协议准备输入，再推进消费。行动选择现场须先通过 `switch_active_character` 或 `declare_round_end` 提供输入；费用预览与支付检查不算输入。库不保存行动的“未选择”标记，也不检查未输入就调用 `step` 的非法用法，上层等待玩家决定期间不推进执行器。

Debug 仅保存最近一次返回的 execution_state，供 view_in 的一致性断言使用；Release 没有这份字段或检查。该断言不承诺发现已失效视图，尤其不能区分两次返回相同种类的现场，因此不为它继续增加 generation 或借用登记。

## 终局

终局只返回 finished。内部向栈顶压入一份 game_result，不附带恢复阶段；旧结算帧已经逻辑废弃，不能再继续重入或当作可观察的活动现场。

公开 `end_game` 指令携带实际结果，不能以 no_result 执行。定义源通过 add_program 编入该指令并保存普通程序入口，不再调用 program_entry 的结果工厂。它与领域指令自身提前决定终局使用同一结果协议，不要求程序必须执行到尾部预定的 end_game。

终局不主动清空栈，不要求沿调用链逐层退出。finished 视图只读取顶层结果；重新 enter_entry 时统一丢弃旧栈并准备入口。这个选择避免沿未完成的调用逐层清理，也避免公开一个可以只清栈却留下执行位置的 clear。
