# 固定程序模型

定义源集（卡牌、角色、状态等规则定义）和游戏流程规则共同编译为一个游戏规则程序。executor 保存当前执行位置和结算中的临时状态，按照这个程序持续推进游戏。

“固定”表示程序中的规则步骤在对局开始前已经确定。运行时可以读取状态、修改事件、选择分支和执行动态数量的领域操作，但不会临时生成一段新的指令序列。

本文说明这一模型对上层和规则拓展者公开的语义。具体指令和事件的字段、执行顺序及栈 ABI 由 [当前指令与事件目录](events.md) 规定。

## 基本约束

- 定义源和游戏流程使用核心公开指令集描述游戏规则程序。
- 指令保存预先确定的操作参数，自身不会在执行过程中改变。
- 对局中持续存在的规则状态保存在 table；当前执行位置和临时结算状态保存在 executor。
- handler 只能选择已经编译的响应程序，不能在运行时构造新的程序。
- 一条公开指令彻底完成后，应当恢复进入该指令时的栈形状；进入终局时保留现场，不要求继续清理。

各段程序在编译结果中如何连接不属于公开接口。只要对局仍在运行，上层通过 executor 观察到的当前指令就必须来自公开指令集。

## 程序入口与 Context

`program_entry<Context>` 表示一段响应程序的入口。`Context` 规定进入该程序时可用的栈 ABI，因此不同 Context 的入口不能互换。例如：

```cpp
program_entry<damage_effect>
program_entry<onpay_context<cost_of_switch>>
```

普通事件响应通常以事件类型作为 Context；支付完成后的效果使用 `onpay_context<CostEvent>`。初始化程序和回合程序不依赖调用者的 Context。

空入口表示“没有响应子程序”。handler 返回空入口时，调用方不会进入其他程序；handler 对 event 已经完成的修改仍然保留。空入口的数值表示不是公开接口。

`program_entry<Context>` 还提供请求 `player_0_win`、`player_1_win` 或 `both_loss` 的具名结果工厂。使用这些结果后，`executor::status()` 返回相应结果，并保留当前结算现场供上层观察。

## 游戏流程与响应程序

游戏流程表示这样的整体运行语义：先执行一次初始化程序，再反复执行回合程序，直到相关领域指令触发对局结束。编译调用方必须提供这两段公开指令序列。

handler 返回的响应程序是一段会回到原结算过程的子程序。响应完成后，触发它的事件广播或领域指令继续执行。响应期间公开可观察的栈布局见 [指令、栈与事件系统](event-system.md)。

定义响应、onpay 响应和游戏流程使用同一套公开指令。公开执行位置始终对应其中一条公开指令；流程之间如何连接不属于上层观察协议。

## 指令与 Context

具体指令通过 `context_type` 声明自己是否依赖调用者的 Context：

- 声明 `using context_type = void` 的指令不读取调用者 Context，可以用于任意程序段。
- 声明 `using context_type = E` 的指令依赖 `E` 的栈 ABI，只能用于 `E` 程序段。
- 没有 `context_type` 的类型缺少静态 Context 信息，不能通过公开程序边界的兼容性检查。

当前一个依赖 Context 的指令只对应一种 Context。若一项操作需要用于多个 Context，其公开语义就不应依赖某一种事件的栈布局。

`any_instruction_for<E>` 是面向定义源的同构指令值。它在构造时检查指令与 `E` 是否兼容，因此动态来源也可以为特定 Context 返回统一类型的 range。`any_instruction_for<void>` 表示无 Context 依赖的同构指令值；这类指令也可以加入具有具体 Context 的程序。统一元素类型不会允许定义源注册新的指令种类。

公开指令集由核心统一定义，目前仍可随规则能力继续补全。拓展者可以组合和配置这些指令，但不能提供核心之外的指令类型。指令执行、重入和栈状态的通用协议见 [指令、栈与事件系统](event-system.md)。

## Handler 与响应

handler 是定义提供的 C++ 响应函数。它可以读取 definition data、自身实体、只读 table 和本次随机输入，并直接修改当前 event。需要修改持久 table 时，handler 返回包含相应效果的程序入口，由公开指令完成修改。

普通 handler 返回 `program_entry<Event>`：

- 返回空入口，只保留对 event 的修改；
- 返回普通入口，执行相应响应程序后继续原结算；
- 返回具名游戏结果，直接结束对局并保留现场。

费用预览与支付后效果分离。费用 handler 修改费用事件，并返回 `program_entry<onpay_context<CostEvent>>`。玩家确认行动后，调用方才进入相应 onpay 程序。当前 onpay 程序只依赖自身 handler 和 `cost_effect_argument<CostEvent>`，不读取已经结束的费用预览栈帧。

## 表达能力

固定程序限制的是运行时生成任意新指令序列，而不是规则的计算能力。

### 固定效果

“对敌方出战角色造成 2 点物理伤害”和“对敌方下一个角色造成 2 点物理伤害”可以由不同的公开指令或不同的指令参数表达。它们都是在编译规则时已经确定的规则步骤。

### 动态数量

一次效果的循环次数、目标数量或消耗数量可以由单条领域指令在执行时读取 event、stack 或 table 后处理，不需要把每次循环展开成独立程序段。

例如层数护盾需要取当前层数与最多消耗层数的较小值，同时修改伤害事件并消耗实体层数。这应由 `damage_effect` Context 下的领域指令一次完成，而不是为每种可能层数准备不同程序。

### 运行期计算

伤害随层数增加、按已损失生命增伤、按目标状态调整费用等规则，通常由 handler 直接计算并修改 event。依赖事件栈 ABI 的公开指令也可以继续修改 event 或产生持久效果，因此不需要额外的指令表达式语言。

### 条件分支

handler 或领域指令可以根据运行时状态选择不同的固定入口。只要分支集合在定义时已知，并且具有明确、较小的上限，这种方式就足以表达条件流程。

真正需要避免的是为无界运行时数值枚举程序段。遇到这类规则，应当把计算放入 handler、事件修改或单条领域指令，而不是随数值增加入口数量。

### 指令粒度

一条公开指令应当表示完整且可观察的最小领域操作。公共算法可以在 C++ 实现中复用，但不应为了复用而把一个领域步骤拆成多次对外可见的内部操作。

## 定义源程序

定义源在 `compile(...)` 中通过受限编译上下文解析已声明依赖，并以 `add_program<Context>(instructions)` 加入响应程序。该操作立即返回强类型入口；定义源把需要的 issued id、程序入口和其他配置一起放入 `compile(...)` 的返回对象，不存在后续 setter 或补写阶段。

每段指令只需顺序遍历一次。native C++ 定义可以提交异构 tuple 或同构 range；动态 adapter 可以提交 `any_instruction_for<Context>` 的同构 range。编译上下文负责检查指令与 Context 的兼容性，但不向定义源暴露程序存储和连接方式。

初始化程序和回合程序以 `context_type = void` 的公开指令序列提供。完整定义源接口和编译顺序见 [编写定义源](definition-system.md)。

## 文档边界

以下内容是公开契约，变化时必须更新文档和测试：

- 指令和事件的字段、语义及执行顺序；
- 输入、挂起、终局与任何可观察栈帧的 ABI；
- handler、程序入口和定义源接口；
- 指令与 Context 的兼容关系；
- 上层可观察的当前指令、随机、复制和清理语义。

程序如何编译、连接和存储不属于本文规定的公开契约。
